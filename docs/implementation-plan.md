# VibeOne 实施计划

本文对应 [架构方案](architecture.md) 与 [主要功能设计](core-functions.md)。当前处于 P0：已完成设计文档、可交互 UI 原型，以及最小插件跨进程链路；真实 Agent 接入与手机后端尚未实施。

## 当前实现进度

| 小功能 | 状态与验证范围 |
| --- | --- |
| TypeScript 插件 SDK | 已实现 Worker 类型契约、JS 导出、Scope 与带代次归属的 Registry；测试覆盖异常清理、重复清理与旧代清理 |
| Node 执行引擎 | 已实现 ESM 加载、清单基础校验、实例与调用上下文、共享进程内多代次、双向 JSON-RPC、进度、取消与超时；真实子进程测试通过 |
| Rust Plugin Host | 已实现 Node 进程监督、握手、双向调用、能力与工作区授权校验、断连失败传播；Rust → Node → Rust 集成测试通过 |
| 工作区工具示例 | 已实现 TS 编译 JS、CLI 调用插件及反向读取明确指定的目录；拒绝宿主 API 的路径越界 |
| 插件动态替换与租约 | 已实现内存路由管理：候选激活成功后发布，失败保留旧路由；已有租约保留旧代次，最后持有者释放后异步清理；禁用阻止新租约 |
| ACP、可靠状态与正式客户端 | 未实现；P0 两工具及真实审批验收仍未完成，不能视为 MVP |

当前 Node runner 使用开发环境的 Node 可执行文件，Rust CLI 使用源码仓库构建路径；打包分发、运行时发现、重启预算、完整依赖解析与公开 SDK 稳定性尚未验收。现有上下文和授权检查不等于恶意插件沙箱。

## 1. 首版验收目标

电脑启动 Host → 桌面选择 Workspace 和 Agent → 发送任务 → 手机配对 → 查看结构化执行进展 → 手机批准/拒绝一次工具权限请求 → 桌面同步结果 → 手机断网重连补齐状态 → 取消任务 → 重新打开桌面仍能查看历史。

必须有两个真实工具跑通共同功能，分别记录各自的适配路径和能力证据；允许两者均使用 ACP 桥接器。初始验证候选为 Claude Code 与 Codex，不把原生 ACP 接入作为首批工具选型的硬性要求。仅有 mock ACP demo 不算 MVP 完成。

## 2. 阶段与出口

### P0：关键路径原型与接口冻结前验证

工作：

- 建最小 Rust CLI ACP Client，验证官方 SDK、stdio 双向调用及进程树管理。
- 选择两个目标工具，锁定工具/桥接器/SDK 版本，验证认证、prompt、更新、取消、审批和 load 能力。
- 先验证 Claude Code 与 Codex 的 ACP 适配路径；记录能力缺口和原工具配置兼容性，不将“存在适配项目”视为已验收。
- 实现最小 Node Worker 与 JS/TS App 插件，测试 initialize、扩展注册、一次调用、取消和退出。
- 做 Host 存活实验：关闭窗口、退出桌面、重新连接、Host 自身崩溃。
- 验证实际手机经可信 HTTPS 访问的部署路径，评估 PWA 安装与通知限制。

产出：兼容矩阵、锁定版本、协议记录样例、接口草案和需要调整的 ADR。遇到审批能力缺口，优先更换首批工具或明确降级，不能用文本解析伪装审批。

出口：两个工具基础链路可用；至少一个真实权限请求可被程序化回应；进程插件与 UI 生命周期实验成立。否则调整方案后再进 P1。

### P1：Host 基础与可靠状态

工作：Cargo workspace、domain/application、实例锁、SQLite 迁移、Run Actor、进程监督、事件游标、命令幂等、取消、审批状态机、outbox、契约生成，以及最小扩展目录、声明式 Provider、Scope 与注册清理。

出口：无 GUI 环境能创建并取消 Run；崩溃后历史可查询，旧审批不会继续执行；关键状态、事件和通知记录同事务提交；不依赖 Tauri 编译。

### P2：桌面闭环

工作：Tauri + React、项目列表、Agent 探测、聊天与工具时间线、审批面板、diff、历史、诊断、Host 连接与托盘，并加载本地 JS 通知 Worker、动态 App 面板及设置表单。

出口：两个工具使用同一套核心 UI；未知/不支持能力有明确展示；关闭窗口不终止运行，退出/停止行为明确；重复发送和取消不会误开多个 Run。

### P3：手机控制与审批

工作：响应式 Web/PWA、配对、设备角色、工作区授权、HTTPS/WSS、审批收件箱、状态查询、发送/取消、断线续传、撤销设备。

出口：真实手机操作通过；桌面和手机竞争审批只成功一次；设备撤销后 HTTP 和已有 WS 均失去权限；旧 cursor 能补齐，过期 cursor 能快照恢复；离线按钮不排队批准。

P3 完成代表核心 MVP，不等待插件市场、原生移动壳或公网中继。

### P4：可对外使用的插件 SDK

P0 验证最小 Worker 与协议，P1/P2 实现扩展目录、声明式 Provider、本地 JS 插件和动态设置 UI；P4 再稳定公开 SDK、完善第三方生命周期和分发，避免过早维护大量公共 API。插件机制本身不推迟到 P4。

工作：Manifest/Schema、依赖解析、Scope、JS SDK 与类型声明、作者构建工具、安装/禁用/升级、grant、进程插件健康检查、声明式表单与代码型 React 插槽、示例 Provider 与通知插件。

出口：新增声明式 ACP 工具无需改 Host；一个 JS 插件能贡献通知与面板，TS 编译产物可由同一 loader 加载；不兼容 API 被拒绝；循环依赖有诊断；故障影响范围与注册清理可验证，共享 Node 退出时准确标记受影响实例；运行中的 Provider 升级不会切断旧 Run。

### P5：远程与并行能力增强

按使用反馈依次选择：Worktree 任务队列、多主机选择、自托管 Relay、可靠推送、原生移动壳、历史导入、WASM 策略插件。每项单独立项验收，不打包成必需大版本。

下表保留最初的整体工作量级估计，作为历史范围参考，不是当前剩余工作量或交付承诺。它未按此次 29 项任务重新校准；先完成 01–06，再结合真实接入结果和实际切片速度更新。原估计按一位熟悉 Rust/React 的全职开发者计算，不含外部审批或商店等待。

## 4. 关键验证矩阵

| 场景 | 必须观察到的结果 |
| --- | --- |
| Agent 初始化不兼容 | 明确错误，不进入 ready，不留下孤儿进程 |
| prompt 等待中收到双向请求 | 文件/权限请求正常响应，不死锁 |
| Agent 启动失败或输出非法帧 | Run 失败原因可见，资源清理 |
| 用户取消后 Agent 不退出 | 宽限期后按策略清理进程树 |
| 手机重试创建 Run | 同 idempotency key 返回同一结果 |
| 两设备同时审批 | 唯一决定，另一方收到当前状态 |
| 决定提交后进程崩溃 | 显示投递不确定，不重放旧审批 |
| Host 重启 | 旧 Run 标 interrupted；按 Agent 能力显式恢复 |
| 断线与慢订阅者 | 主流程继续；重连后事件去重、补齐 |
| 越权设备或被撤销连接 | 服务端拒绝，现有订阅停止 |
| 插件超时/崩溃 | 不阻塞审批核心，不变成自动允许 |
| 插件卸载 | 订阅/注册释放；运行 Provider 先排空 |
| 文件越界与符号链接 | Host API 拒绝未授权访问 |
| 同仓库并行写 | 默认阻止冲突，或明确分配独立 Worktree |

优先对状态机、事务竞争、权限和协议集成写有意义的测试；UI 以关键流程和真实设备验收为主。准备可控假 Agent 模拟畸形帧、超时、并发权限和异常退出，再用两个真实工具验收，避免所有测试依赖外部模型服务。

性能以可复现负载定义：记录事件条数、消息大小、会话数、机器配置；再制定时间线渲染、重连和内存预算。P0 前不宣称某个吞吐数值已达到。

## 5. 开工顺序

最小进程插件和 Rust 插件 CLI 已具备。下一步从任务 01 建立独立的 ACP 客户端与假 Agent，再依次验证真实对话、真实权限请求和两工具能力差异；不让 Plugin RPC 代替 Agent ACP。接入验证后建设可靠 Host，再连接 Tauri UI，具体依赖以本地任务总览为准。
